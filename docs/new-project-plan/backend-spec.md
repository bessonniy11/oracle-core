# Oracle Core: Спецификация бэкенда

Документ описывает требования к серверной части Oracle Core. Цель — обеспечить стабильный API для фронтенда, голосовых сценариев и управления персонами/правилами.

## 1. Архитектура
- Node.js + TypeScript.
- Web-фреймворк: старт с Express.js; допускается миграция на NestJS без изменения публичного API.
- ORM: TypeORM (PostgreSQL). Миграции обязательны.
- Слои: HTTP → контроллеры → сервисы → репозитории → БД/интеграции (AI, STT/TTS).
- Валидация входа через schema (zod/joi/class-validator).
- Логирование: pino/winston в JSON; уровни info/error/warn; correlation-id на запрос.
- Rate limiting: per-IP/per-user на запись (чаты/правила/персоны).

## 2. Данные и модели
- Пользователь/Сессия (позже auth): id, device/session-id.
- Персона: id, name (уникальное в рамках пользователя), system_prompt, is_default (bool), created_at, updated_at.
- Правило: id, persona_id (FK), content, order, created_at, updated_at.
- Чат: id, persona_id (FK), title, created_at, updated_at.
- Сообщение: id, chat_id (FK), role (user|assistant|system), content, created_at; optional audio_url, tts_state.
- Ограничения:
  - name ≤ 64 символов; prompt ≤ 8000 символов; правило ≤ 2000 символов.
  - Максимум персон на пользователя: 10; правил на персону: 50; сообщений на чат (хранение) — пагинация с лимитом 50 за запрос.

## 3. API (REST)
Все ответы в JSON; коды: 2xx success, 400 валидация, 401/403 auth, 404 not found, 429 rate limit, 5xx ошибки.

### 3.1. Здоровье
- `GET /health` — liveness.
- `GET /health/ready` — проверка БД/внешних сервисов.

### 3.2. Персоны и правила
- `GET /personas` — список персон с правилами (можно без контента правил, по флагу `includeRules`).
- `POST /personas` — создать; body: name, system_prompt, is_default? (единственная).
- `PATCH /personas/:id` — обновить имя/промт/флаг по умолчанию.
- `DELETE /personas/:id` — удалить (если нет is_default).
- `POST /personas/:id/rules` — добавить правило; body: content, order?.
- `PATCH /personas/:id/rules/:ruleId` — обновить контент/order.
- `DELETE /personas/:id/rules/:ruleId` — удалить правило.
- Валидация: уникальность имени на пользователя; лимиты из раздела 2.

### 3.3. Чаты и сообщения
- `GET /chats` — список чатов (id, title, persona_id, updated_at).
- `POST /chats` — создать; body: persona_id, optional title.
- `DELETE /chats/:id` — удалить чат вместе с сообщениями.
- `GET /chats/:id/messages?cursor&limit` — история с пагинацией (по updated_at/created_at).
- `POST /chats/:id/messages` — отправить сообщение пользователя; body: content, optional audio_url.
- `POST /chats/:id/messages/:msgId/resend` — повторить запрос к AI (если предыдущий упал).
- При создании сообщения сервер вызывает AI и пишет ответ модели как отдельное сообщение (role=assistant).

### 3.4. AI-интеграция
 - Внутренний сервис: `POST /ai/completions` (не публичный для фронта) - вход: persona_id, messages[], правила, максимум токенов. Ответ: text, usage, safety_flags.
 - Должен обогащать системным промтом персоны + правилами.
 - Время ожидания: таймаут 20-30 секунд; при превышении возвращать 504 + ссылку на повтор.
 - Модель по умолчанию: `gemini-2.5-flash` (бесплатный стартовый тариф). Модель выбирается через конфиг/ENV без правок кода.

### 3.5. Голос (опционально через бэкенд)
- `POST /voice/stt` — принимает audio_url/base64, возвращает text. Таймаут и лимит размера аудио (например, ≤ 1 МБ, ≤ 20 сек).
- `POST /voice/tts` — принимает text, возвращает audio_url/base64 или streaming; при ошибке — текстовый ответ.

## 4. Ошибки и ответы
- Единый формат ошибки: `{ error: { code: string, message: string, details?: any } }`.
- Не раскрывать стеки/ключи. Для 5xx — общее сообщение.
- Валидационные ошибки — массив полей.

## 5. Безопасность
- CORS только для доверенных origin (конфиг).
- Env через `.env`, без логирования секретов.
- Ограничение размера тела (например, 1 МБ JSON).
- Защита от prompt injection минимально: обрезка длины входов, экранирование, не логировать сырые промты с PII.
- CSRF не актуален для mobile/native; для web — через токен/заголовок (если появится cookie-based auth).

## 6. Логи и аудит
- Логировать: запрос/ответ (метаданные, без контента), ошибки, обращения к AI (latency, токены).
- Correlation-id из заголовка `x-request-id` или генерировать.

## 7. Конфигурация окружений
- `NODE_ENV`, `PORT`.
- `DATABASE_URL`.
- `AI_API_KEY` (Gemini, модель по умолчанию `gemini-2.5-flash`, выбирается через конфиг).
- `STT_API_KEY`, `TTS_API_KEY` (если используются внешние).
- `CORS_ORIGINS`, `RATE_LIMIT_PER_MIN`.

## 8. Тестирование
- Unit: сервисы и валидации.
- Интеграционные: API + БД (in-memory/тестовый контейнер).
- Контрактные тесты для AI-обёртки (мокаем HTTP).
- E2E (позже): smoke по основным флоу (создать персону, чат, отправить сообщение, получить ответ).

## 9. Миграции и сиды
- Все изменения схемы — через миграции.
- Сид для дефолтной персоны и примерных правил (только в dev/test).

## 10. Производительность и лимиты
- Пагинация обязательна для историй.
- Таймауты HTTP (30s) и к внешним сервисам (20s).
- Ограничения на длину промтов/правил/сообщений см. раздел 2.

## 11. Наблюдаемость
- Метрики (latency, ошибки, rate limit срабатывания) — прометеевский формат или логи для парсинга.

## 12. Документация и комментарии
- Весь код бэкенда покрывается JSDoc/TSdoc-комментариями на русском языке: описание функций/методов, параметров, возвращаемых значений, возможных ошибок.
- Ключевые модули и сложные участки (интеграции с AI/STT/TTS, репозитории, валидация) сопровождаются краткими комментариями, поясняющими назначение и поток данных.
- Публичные интерфейсы/DTO/сервисы документируются так, чтобы по комментариям было понятно, за что отвечает модуль и как его использовать.
