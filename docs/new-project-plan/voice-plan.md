# План внедрения новых голосов (TTS)

## 1. Контекст и текущие ограничения

- В веб-версии используется Web Speech API, список голосов определяется браузером и ОС.
- Набор русских голосов в браузере ограничен установленными системными пакетами.
- Репозитории/демо (например xiaozhi) не содержат «голоса» как переносимые модели; чаще всего это прокси к облачным TTS.

## 2. Цель

- Добавить качественные русские голоса сверх системных.
- Сохранить управляемость: выбор голоса для каждой персоны.
- Обеспечить стабильный TTS в web + mobile.

## 3. Варианты

1. Системные голоса (текущий MVP)
2. Облачный TTS (предпочтительно)
3. Self-hosted TTS (позже, если нужно офлайн/контроль)

## 4. Предпочтительный путь: облачный TTS

1. Выбрать провайдера (Google Cloud TTS, Azure TTS, Yandex SpeechKit, ElevenLabs и т.д.)
2. Создать TTS-микросервис в backend (endpoint: /tts)
3. На фронте заменить Web Speech API на воспроизведение аудио из /tts
4. Добавить кэширование (по text+voice+settings)
5. Ввести лимиты и мониторинг (rate-limit, таймауты, fallback)

## 5. Минимальный MVP для облака

1. В backend добавить сервис генерации аудио (sync/async)
2. Возвращать mp3/ogg + metadata (voice, duration)
3. На фронте:
- запрашивать /tts при озвучивании
- проигрывать через стандартный аудиоплеер
- добавить «Стоп» и корректное прерывание

## 6. Технические требования

- API ключи хранятся только на backend
- CORS: разрешать домены фронта
- Ограничения: размер текста, длина аудио, скорость генерации
- Логи: метрики latency, ошибки, частота запросов

## 7. Риски и компромиссы

- Стоимость за символы
- Задержки (latency)
- Зависимость от провайдера
- Политика хранения данных

## 8. Фолбэк

- Если TTS недоступен: использовать системный TTS (Web Speech) или отключать озвучку
- Явное сообщение пользователю о недоступности TTS

## 9. Этапы внедрения

1. Согласовать провайдера и бюджет
2. Реализовать backend /tts + тесты
3. Обновить frontend (web + mobile)
4. Прогон регрессии (озвучка, пауза, стоп, длинные тексты)
5. Документация и мониторинг в проде
