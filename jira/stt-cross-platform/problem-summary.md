# Проблема: почему не работает "везде одинаково"

## Наблюдаемое поведение

- На ПК в браузере микрофон работает.
- На Raspberry в Chromium:
  - доступ к микрофону (`getUserMedia`) есть,
  - `SpeechRecognition` стартует, но падает с `error: network`.
- В Linux desktop приложение запускается, но голосовые ответы не воспроизводятся ожидаемым способом через `audioUrl`.
- В Android APK (нативный запуск приложения):
  - в чате не применяется голос персонажа, выбранный в настройках (Piper),
  - фактически всегда звучит голос по умолчанию.
- При этом в Android браузере (web-версия `https://oracle.ibessonniy.ru/#/chat`) выбранный голос персонажа применяется корректно.
- В iOS браузерах (Safari и Chrome):
  - сообщения ассистента приходят текстом, но не воспроизводятся голосом в чате,
  - при этом preview в настройках работает и корректно воспроизводит Piper-голоса.

## Подтвержденная первопричина

- Текущий STT в web завязан на Web Speech API (`webkitSpeechRecognition` / `SpeechRecognition`), который нестабилен/ограничен в части ARM Chromium и зависит от внешних сервисов распознавания.
- Текущий голосовой контур различается между платформами:
  - web умеет проигрывать `audioUrl`,
  - desktop/mobile не используют `audioUrl` как основной источник (fallback на локальный TTS).
- В Android APK это приводит к функциональному рассинхрону с web:
  - сервер генерирует `audioUrl` с нужным голосом (Piper),
  - но путь воспроизведения в приложении уходит в локальный TTS/fallback, из-за чего голос персонажа игнорируется.
- В iOS web наблюдается типичное ограничение браузерного autoplay/gesture policy:
  - воспроизведение `audioUrl` в чате запускается не из явного пользовательского жеста,
  - поэтому аудио может блокироваться, даже если тот же URL успешно играет в preview (там запуск обычно происходит по кнопке пользователя).
- Итог: функциональность зависит от окружения, а не от продукта.

## Почему Firefox сам по себе не решит задачу

- В Firefox Web Speech API либо отсутствует, либо не дает совместимого поведения для данного сценария.
- Переход на Firefox не убирает системную зависимость от браузерного STT.
- Это не архитектурное решение, а временный эксперимент с низкой предсказуемостью.

## Риск, если оставить как есть

- Пользовательский опыт ломается на части устройств (особенно Raspberry/ARM).
- Диагностика сложная: "разрешения есть, но не работает".
- Невозможно гарантировать SLA для голосового ввода.

## Целевое решение

- Основной канал STT перенести в backend (streaming или near-real-time).
- Основной канал TTS в клиенте — воспроизведение серверного `audioUrl`.
- Локальный Web Speech / OS TTS оставить только как fallback.
- Добавить телеметрию и явные статусы в UI.

## Ожидаемая задержка при STT через backend

- Да, дополнительная задержка появляется, но она контролируема.
- При потоковом STT и VAD задержка обычно укладывается в приемлемый UX:
  - частичные гипотезы: ~150-600 мс,
  - финал фразы: ~400-1500 мс (зависит от модели/железа/сети).
- При правильной архитектуре UX часто лучше, чем у нестабильного браузерного STT.
