# Спецификация проекта Oracle Core (Фаза 1: Тестирование логики)

## 1. Введение
Данный документ описывает функциональные и нефункциональные требования, а также высокоуровневую архитектуру для первой фазы проекта "Oracle Core" — разработку и тестирование основной логики персонализированного AI чат-робота без привязки к физическому устройству.

## 2. Функциональные требования

### 2.1. Управление персонами
*   **2.1.1. Определение персон:** Система должна позволять определять несколько именованных "персон" (например, "Афина", "Фортуна"). Каждая персона будет иметь уникальный набор характеристик и поведения.
*   **2.1.2. Базовые промты:** Каждой персоне должен быть присвоен начальный системный промт (инструкция), который будет определять её роль и стиль общения по умолчанию. Например, "Афина - помощник программиста", "Фортуна - юморист".

### 2.2. Диалог с ассистентом
*   **2.2.1. Распознавание обращения:** Система должна уметь распознавать, к какой персоне адресовано сообщение пользователя, если в сообщении явно указано имя персоны (например, "Афина, как написать код...").
*   **2.2.2. Выбор персоны по умолчанию:** Если имя персоны не указано, система должна использовать персону по умолчанию.
*   **2.2.3. Поддержание контекста:** Ассистент должен "помнить" историю диалога для каждой активной персоны, чтобы обеспечивать связность и релевантность ответов.
*   **2.2.4. Генерация ответов:** Система должна генерировать ответы на основе текущей персоны, её промтов, динамических правил и истории диалога.

### 2.3. Динамические правила
*   **2.3.1. Добавление правил:** Пользователь должен иметь возможность добавлять новые правила для конкретной персоны прямо во время диалога. Формат добавления правила будет определяться (например, "Фортуна, запомни вот такое правило <текст правила>").
*   **2.3.2. Применение правил:** Добавленные правила должны автоматически включаться в промт AI-модели при генерации ответов для соответствующей персоны.

### 2.4. Интеграция с AI-моделью
*   **2.4.1. Использование Google Gemini API:** Для генерации ответов будет использоваться Google Gemini API.
*   **2.4.2. Формирование запросов:** Запросы к Gemini API должны динамически формироваться на основе системных промтов персон, добавленных правил и истории диалога.

### 2.5. Пользовательский интерфейс (для тестирования)
*   **2.5.1. Веб-интерфейс:** Будет разработан простой веб-интерфейс (HTML/CSS/JS) для имитации взаимодействия с чат-роботом.
*   **2.5.2. Ввод сообщений:** Интерфейс должен иметь поле для ввода текстовых сообщений пользователя.
*   **2.5.3. Отображение диалога:** Интерфейс должен отображать историю переписки (сообщения пользователя и ответы ассистента).

## 3. Нефункциональные требования (для Фазы 1)

### 3.1. Производительность
*   **3.1.1. Время ответа:** Ответы от ассистента должны поступать в разумные сроки, не превышающие 5-10 секунд, включая время на обработку запроса AI-моделью.

### 3.2. Масштабируемость
*   **3.2.1. Расширяемость:** Архитектура должна быть спроектирована таким образом, чтобы в будущем можно было легко добавлять новые персоны, типы правил и интегрировать другие AI-модели.

### 3.3. Безопасность
*   **3.3.1. Защита API-ключей:** API-ключи для доступа к AI-моделям должны храниться безопасно (например, через переменные окружения) и не должны быть жестко закодированы в приложении.

### 3.4. Надежность
*   **3.4.1. Обработка ошибок API:** Система должна корректно обрабатывать ошибки при взаимодействии с внешними AI-API (например, таймауты, ошибки авторизации, превышение лимитов).

### 3.5. Удобство тестирования
*   **3.5.1. Локальное развертывание:** Приложение должно легко разворачиваться и запускаться на локальной машине для удобства разработки и тестирования.

## 4. Архитектура (Фаза 1)

### 4.1. Backend (Серверная часть)
*   **Технология:** Python 3.x, Flask.
*   **Функционал:**
    *   REST API для взаимодействия с Frontend.
    *   Обработка входящих пользовательских сообщений.
    *   Управление состояниями персон (активная персона, история диалога).
    *   Парсинг сообщений для определения обращения к персонам и добавления правил.
    *   Формирование комплексных промтов для AI-модели.
    *   Взаимодействие с Google Gemini API.
    *   Временное хранилище (в памяти или JSON) для персон, их правил и истории диалогов.

### 4.2. Frontend (Клиентская часть)
*   **Технология:** HTML, CSS, чистый JavaScript.
*   **Функционал:**
    *   Простая веб-страница.
    *   Элементы UI для ввода текстовых сообщений.
    *   Область для отображения истории диалога.
    *   JavaScript-код для отправки HTTP-запросов на Backend и обновления UI.

### 4.3. Взаимодействие
*   Frontend отправляет пользовательские сообщения на Backend через HTTP POST запрос.
*   Backend обрабатывает сообщение, взаимодействует с Gemini API и возвращает ответ, который Frontend отображает пользователю.

## 5. Выбор технологий

*   **Язык программирования:** Python (Backend), JavaScript (Frontend).
*   **Веб-фреймворк:** Flask (Backend).
*   **AI API:** Google Gemini API.
*   **База данных (для Фазы 1):** Временное хранение в памяти / JSON-файле (для простоты прототипирования).
